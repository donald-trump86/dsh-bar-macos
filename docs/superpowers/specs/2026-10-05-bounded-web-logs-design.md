# DSH Web 日志限额与 0.1.5 发布设计

## 目的与确认范围

用户要求解决 `~/.dsh/logs/dsh-web.log` 长期累积的问题，删除现有无用大日志，递增版本，推送 GitHub 并发布。已确认每份 10 MiB、保留两份历史；进一步确认独立后台写入方案，使退出 Bar、保留 Web 服务时仍能轮转。当前版本 0.1.4，目标版本 0.1.5。

成功标准：新启动的托管 Web 服务，无论 Bar 是否退出，日志总量均不超过 30 MiB；输出中没有换行或单次输出大于限额也不会突破限额。Web 的真实 PID、端口、身份校验和现有退出语义不变。无需第三方依赖、系统守护服务配置或设置界面。

## 现状与根因

- `Sources/ServiceManager.swift` 的 `launchProcess(path:port:)` 用普通文件句柄 `seekToEndOfFile()`，把 Web 的 stdout/stderr 指向同一个文件，既没有轮转，也没有追加标志。
- 2026-10-05 检查的旧日志为 888411173 字节（约 847 MiB）。日志中反复出现 `RangeError: Maximum call stack size exceeded`，错误附带大段压缩源码，加速了增长。修复第三方插件的递归错误不在本次范围。
- 对活动文件直接 unlink/rename，进程仍写入旧 inode；截断非追加句柄则可能产生稀疏文件。Bar 定时器在退出时停止，不能持续限制保留的后台 Web。
- 实时窗口目前只检查文件大小变小，不能识别新文件已经长到旧偏移以上的轮转。

## 数据流与职责

```
Web stdout + stderr → 一条 Pipe → 独立 dsh-bar 日志模式 → 当前文件 / .1 / .2
Bar → 启动 Web（真实 Process/PID）和日志模式，读取有限的启动控制消息
```

新增 `Sources/RotatingLogWriter.swift` 承载日志写入和日志子进程启动支持；`Sources/main.swift` 在访问 `NSApplication` 前识别内部日志模式参数。日志子进程使用同一个已签名可执行文件，不创建另一个安装组件。

日志模式只使用 Foundation/Darwin：脱离 Bar 的终端会话，忽略 SIGHUP；一个串行读取/写入循环负责所有轮转。普通退出只结束 Bar，绝不终止日志子进程或 Web。Web 停止且所有继承输出管道关闭后，日志子进程读到 EOF、关闭文件并退出。日志子进程被强制杀掉仍可能导致 Web 输出失败，这是管道方案的已知边界，不声称容忍任意 logger 崩溃。

## 文件限额与所有权

- 当前文件 `dsh-web.log`，历史文件 `dsh-web.log.1`、`dsh-web.log.2`，每份上限 `10 * 1024 * 1024` 字节。满额后，收到下一字节前关闭当前句柄、删除最老文件、依次移动历史文件并创建新的当前文件。
- 读取固定大小块；按剩余容量拆分写入，处理 EINTR 和短写。不按行缓冲，不把整个日志载入内存。三个文件合计上限 30 MiB；稳定历史下实际保留量随当前文件增长为 20–30 MiB。
- 目录权限 0700，所有日志、锁文件权限 0600。轮转只触及上述固定文件，绝不批量删除其他 DSH 日志。
- 单独持久锁文件使用 lifetime `flock` 防止重启重叠/多个 Bar 实例同时轮转；锁描述符不跨 exec 继承，锁文件本身不删除。等待锁和启动握手均有明确超时，不无限等待。
- 每次新日志进程获得锁后，将已有非空当前文件轮转，为本次启动建立新的文件。离线超大历史只保留最多 10 MiB 的尾部，不把超大文件完整保留为历史。不能在旧版非协作写入者仍持有文件时这样迁移；升级清理需先停止旧写入者。

## 启动、控制消息与错误

`ServiceManager` 仍直接启动实际 `dsh web --no-open`，不把日志子进程当成 Web PID。先启动日志子进程，等待其成功取得锁并打开文件的就绪消息，才启动 Web。父进程随即关闭自己持有的输出 Pipe 两端；Web 和日志子进程各保留必要端点。所有异常路径关闭不用的端点，避免日志进程永远无法读到 EOF。

有限的独立控制管道报告就绪以及本次启动的认证 URL。日志进程从固定上限的启动输出中识别 URL，只接受目标端口、localhost/127.0.0.1；父进程只信任本次启动控制管道，不再从轮转历史挖 token。控制管道关闭不会让 logger 被 SIGPIPE 杀死；token 只在内存保留，不写入额外文件或界面。启动输出未捕获有效 URL 时回退到普通 base URL。

日志打开/锁/就绪失败：不启动 Web，走现有 launchFailed 错误路径。Web 启动后 PID 文件写入等失败：清理此次新建的 Web 和父管道端点，不留下无记录的服务。正常停止不粗暴杀 logger，而让其排空输出并释放锁；下一次启动有限等待旧进程完成。

运行中磁盘满、权限或轮转失败：停止写日志、报告有限的错误并继续读取丢弃输出，保持 Web 不被管道堵住，绝不退回无限增长的直接文件写入。丢弃只用于磁盘故障，不用于正常轮转。下一次显式重启可以重试日志初始化。

## 实时日志窗口

`Sources/LogWindow.swift` 在后台读取时记录文件 device/inode，并以打开的句柄为准取得身份/大小。身份改变或大小下降时，从新文件尾部重新读取；沿用现有有限内存缓冲、暂停、搜索和 token 脱敏。处理暂停期间多次轮转和新文件快速长到旧偏移以上的情况，不依赖仅比较 pathname 的大小。

## 验证

提供一个可执行、无第三方框架的检查，挂入 `make check`，直接编译/调用实际日志代码而不是重复实现：

1. 精确阈值、空输出、单次超大无换行输出、持续输出超过 35 MiB；每份不超过 10 MiB、历史数量为二，按 `.2 + .1 + 当前` 拼接等于原输出相同长度的尾部。
2. 关闭/结束模拟 Bar 父进程后继续生产输出，日志子进程仍轮转；EOF 后退出释放锁，连续启动可接管，锁冲突有限失败。
3. 启动失败清理、故障后继续排空输出、控制管道提前关闭，文件权限。
4. 启动认证 URL 在轮转后仍可通过本次控制管道获取；不接受其他端口/历史 token。
5. 文件身份变化且新文件大小不小于旧偏移时，窗口的读偏移仍正确重置；构建检查窗口集成。

运行现有 `make check`，构建并验证 arm64/x86_64 通用应用、版本、最低系统版本和签名。

## 旧日志清理与发布

用户已明确授权删除旧日志。清理前重新确认绝对路径和写入者；当前 Web 承载本次会话，不在回复前直接杀掉。可用独立受管理的后台迁移任务在延迟执行/会话安全交接后停止已核验的旧写入者、确认旧 inode 无写入者，再删除旧日志并重新启动正确服务；若安全重启无法确认，则单独说明阻碍，不谎称已清理或已部署。仓库代码发布不依赖本机安装更新，用户没有要求替换 `/Applications` 中的应用。

同时修改 `Info.plist` 两个版本字段为 0.1.5，更新 README 的版本例子及日志规则。提交经验证的代码，创建 `v0.1.5` 标签，非强制推送 main 和标签。由现有 Release workflow 构建并发布 `DSH-Bar-0.1.5-universal.zip` 与 `.sha256`。等待工作流完成，检查 Release 非 draft、目标提交和资产。按仓库现有规则 0.x 标记 pre-release；无 Developer ID 配置时明确为 ad-hoc、未公证，不承诺 Gatekeeper 直接放行。
